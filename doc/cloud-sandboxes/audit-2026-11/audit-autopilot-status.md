# Audit: autopilot loop and what the app says about it

Scope read: autopilot/{mod,state,github_wait,local}.rs, next_actor.rs, attention.rs, stop_questions.rs, phase.rs, gate/derived.rs, lifecycle_next.rs, pr_readiness.rs, conversation/{protocol,phase,implement,verify,review,fix,pr}.rs, task panel (the file is `unified/panels/task.rs`, not task_panel.rs), runners.rs, attention_feed.rs, views/cloud_node.rs, views/task_list/standing.rs, store waits/activity/cloud_activity/decisions, plus (because the cloud path lives there) tod-supervisor, tod-orchestrator wakes/answers/github_gate/webhooks, cloud_sync.rs and cloud_sync/lost.rs.
Not audited: lifecycle_validity.rs, usual_actions.rs, evaluate-specific prompt text. Nothing was run; every claim is from reading code (all paths relative to /Users/jshellman/dev/tools/tod). Items marked "verify" are inferred, not observed.

Key structural fact behind most findings: for a node whose sandbox is live, `next_actor::compute` deliberately ignores the node's autopilot file (next_actor.rs:379, `row.lost_at.is_none()`), and the supervisor never writes its `Outcome` anywhere synced (tod-supervisor main.rs prints it with eprintln; lib.rs:478 returns it). The app's only knowledge of a cloud run is: the `cloud_activity` heartbeat (live / idle / stale), pending decisions, plan steps, findings, pending waits. Everything else the supervisor concludes is invisible.

---

## 1. Every cloud stop that is not a decision, plan step or finding leaves no trace; the node reads "not started" with Sync now as the only button
Severity: blocks-work
Where: tod-supervisor/src/lib.rs:441-445 (only `AgentFailed` and `BudgetExhausted` ask; `_ => break Ok(outcome)`); next_actor.rs:515 (no `last_outcome` for cloud nodes) and the final `NotStarted` arm (~l.585); task.rs:737-775 (`runner_actions_for_place` for a cloud node: primary = Sync now, menu = Run with a new session / Reinstall / ...).
Scenario: the supervisor ends a wake with `NeedsHuman::{PrStuck, PrBlocked, NoProgress, EvaluationStuck, NoPlan, FailingCriteria, GateNotPassed, Permission}` or `Stopped` for any reason other than a wait. Heartbeat goes `idle` (beat.rs `end_cloud_beat`), no wait row, no attention item. `derive` falls through to `You { NotStarted, since: entered_at }` ("on you: not started, waiting 3d"). The user gets no reason and no action: Sync now re-wakes the supervisor, which re-enters the same loop and stops at the same place with nothing spent (e.g. PrStuck: `pr_turns_base` and the turn count are unchanged, mod.rs:760-768, so `pr_stuck` fires again at once). The only thing that resets the PR round counter is `Autopilot::renew_budget` (mod.rs:329), which no cloud code path calls; "Run with a new session" does not reset it either (`start_fresh_session`). So PrStuck is a permanent dead end in the cloud.
Specific cases worth naming: `FailingCriteria`/`GateNotPassed` are classed `is_request()` (mod.rs:195) as "answered where requests are answered", but `attention` has no source for gate criteria (attention.rs: decisions, plan steps, findings only), and nothing in the task panel mentions criteria, so they appear nowhere. `NoProgress { step }` renders with internal step names ("fix_failed changed nothing", "gate_check", "phase", "evaluate", mod.rs:225 and `step_name`).
Fix: have the supervisor record a durable, synced stop record when `run` returns anything that is not Done/Waiting/Stopped-by-hook: either reuse `stop_questions` (ask a decision "The run stopped: <describe()>. Keep going / Leave it stopped" with a new kind, which already syncs and pokes on answer) or add a `cloud_activity.stopped_reason` column written in `Beating::end`. In `next_actor::actor_for` map that to `YouReason::Stopped { reason }` (the same mapping `outcome_reason` does for local). Add a cloud "Resume" action that calls `renew_budget` through the same answered-decision mechanism (an answer of "Keep going" => supervisor calls `pilot.renew_budget()` when acting on it, supervisor answers.rs `before_wake`). Rewrite `NeedsHuman::describe` for plain words per variant and drop step names.
Regression test: yes. next_actor.rs `mod tests` (a Facts-level case with the new stop field); tod-supervisor/tests/answers.rs for the supervisor side.

## 2. "Leave it stopped" is permanent, silent, and swallows every later user action; the app shows "not started"
Severity: blocks-work
Where: tod-supervisor/src/lib.rs:303-312 (the `LeftStopped` return happens before the fresh-session request is looked at at ~l.322); answers.rs:74 (`Answer::Stop` => `LeftStopped`); stop_questions.rs:73 (`latest`: only the node's newest stop-kind question counts, "leave" is sticky until the user re-answers it); task.rs:868-877 + views/cloud_node.rs:125 (`Ok((said, true))` => "Asked for a new session").
Trace for `remediate-stale-primary-lifecycle-stat-2` (planning, answered "Leave it stopped", 06:09 wake printed "left stopped (the user left it stopped (supervisor:budget))"):
- `next_actor::compute`: the node has a cloud_nodes row with `lost_at` None, so the stale local autopilot file is ignored. Leases: none. Cloud beat: `idle` (LeftStopped calls `end_cloud_beat`), so not live and not stale. Attention: the only pending decision is on another node, so none. Waits: none pending (assumption; if a stale one exists see finding 3). Result: `You { NotStarted, since: <entered planning> }`: "on you: not started, waiting Nh". Not "working", not idle, but wrong in the way that matters: it never says "you told it to stay stopped". Nothing in `next_actor` reads `stop_questions::latest`.
- The `autopilot/<node>.json` in the sandbox says `needs_human, decision pending 1` from 04:06 because the LeftStopped wake exits before `Autopilot::new`, so that file is never rewritten; and the app never reads it for cloud nodes. It is a stale private file, not a database fact.
- "Run with a new session": the app writes a `fresh-session` file and pokes; the supervisor exits on the stored Stop answer first; the app's `supervisor_heard` counts the idle stamp as a report and tells the user "Asked for a new session". The file stays in the state dir and will fire unexpectedly the next time the node is allowed to run. Likewise "Sync now" and every poke from context changes, answers to other decisions, wait changes and webhooks all wake a supervisor that immediately exits LeftStopped.
- The way out exists (Answered drawer, Change the answer to "Keep going", the orchestrator pokes on `decision_answers`), but nothing points to it.
Fix: (a) `next_actor::for_nodes` loads `stop_questions::latest` per node (batched, same crate) and yields `YouReason::Stopped { reason: "you left it stopped after the budget question; Keep going resumes it" }` when the latest answer is Stop (above the NotStarted fall-through, below Working). (b) Task panel: for that standing offer "Keep going" as the cloud primary action; it appends an answer to the latest stop decision (`DecisionRepo::answer`) and the existing orchestrator poke does the rest. (c) Supervisor `before_wake`: a `fresh-session` file or an answer newer than the stop answer must not be swallowed; at minimum, if it returns LeftStopped with a fresh-session file present, delete the file and record why; and `wake_node_tracked_with` must not report success when the heard report is a LeftStopped idle (e.g. beat `what = "left-stopped"` instead of plain idle). (d) Reword the question (finding 12).
Regression test: yes. next_actor.rs tests (Facts + stop answer); tod-supervisor/tests/answers.rs (fresh-session file with a Stop answer); cloud_sync tests for the success/failure message.

## 3. Pending waits never expire or cancel; stale ones turn a stuck node into "On others: check overdue" and (when future-dated) stop the autopilot
Severity: wastes-time (blocks-work when the stale wait is future-dated)
Where: tod-store/src/waits.rs:`list_pending_for_nodes` (read by next_actor.rs:319 only, plus supervisor waits.rs:46/92, runner_status.rs:76 `github_wait`, github_wait.rs cancel/replace, orchestrator `github_gate`, `wait_changes`); lifecycle/mod.rs `advance`/`revert`/`revert_to` (never touch waits); only expiry in the system: tod-supervisor/src/waits.rs:92-102 (`check`, on a supervisor wake, and only for that node's replica); github_wait.rs:455 `cancel_waits` (prefix-matched, only called from approved/merged/pr_draft looks and babysit); `clear_poll_waits` (github_wait.rs:408) matches `github:pr:` but not the agent-written `github:pr 2810 checks` spelling (space form; `tod-cli wait` docs use it, webhook `spec_matches` accepts either).
Why the 11 rows are stuck: they were recorded (by the autopilot in `pr_draft`: `github:pr:6375:ready_for_review`; by agents: `github:pr 2810 checks`), the node then left that state by a route that does not call the waiting code (human force-advance, move-back, a supervisor that no longer exists, `deleted_by_user` sandbox whose wake poke returns `SandboxGone` and the wake row is dropped, wakes.rs `fire_due`). The orchestrator `GithubGate` runs `check_github` for the node's *current* lifecycle, which is `NothingToWaitOn` outside approved/merged/pr_draft, and then pokes (a dead sandbox) instead of cancelling.
Wrong answers produced:
- next_actor.rs:565: any pending wait wins over `NotStarted`, so a node that is sitting un-started in `planning` shows a diamond "waiting on others: something outside (or a person's review/bot...), check overdue". Alt+Q skips it (`on_you` false), the strip counts it under "On others", and `Others` is documented as "resolves without the user". It never does.
- `overdue` (next_actor.rs:631) uses `due_at - updated_at` as the poll interval and allows 2x that: for an agent wait with the default 24h deadline a missed look is only flagged after 48h; the 11 rows are flagged but still read as `Others`, not as a fault.
- Future-dated stale wait (agent `--deadline 24h`, or a usage-limit `until`): the supervisor's `Hook::at` (lib.rs ~l.196-201) and the pre-run check in `wake` (lib.rs ~l.322) return "waiting" for ANY pending wait, so the run stops at every boundary until it comes due even though the state moved on. Nothing says it is stale.
- `runner_status::github_wait` shows a "next poll" line and offers Poll now for a wait that belongs to a state the node left.
Fix rules (implement as one `tod_store::waits::sweep` called from the places listed):
1. On lifecycle advance/revert/revert_to (and node delete / leave-cloud / `retire_done`): cancel the node's pending waits whose spec is `github:*` or whose kind is `event`/`check`, except `until` waits recorded by the usage-limit path. Do it inside `lifecycle::advance`/`revert*` so no caller can forget.
2. Expire past-due `event` waits that no scheduler can serve: in `next_actor::compute` input stage (or the daemon `reconcile`) set `expired` when `due_at + grace < now` AND the node is not a live cloud node (no row, or `lost_at` set) AND no local run is waiting on it. For live cloud nodes the supervisor's `check` already does it on wake.
3. Startup sweep in the app and orchestrator: pending waits for nodes that are `done`, deleted_by_user, or in a lifecycle that none of the wait's spec families belongs to (`github:pr:*:ready_for_review|review_requested` only valid in pr_draft; `:review`, `bot-review`, `checks` only pr_draft/pr_review; `:merged` only approved; `github:release:*` only merged).
4. `derive`: a pending wait must not outrank `NotStarted` if it is past due by more than 2 poll intervals; show `You { Failed/Stopped: "its wait on X was due Nd ago and nothing is looking" }`.
5. Make `clear_poll_waits`/`cancel_github_waits` normalise `github:pr N` to the colon form.
Regression test: yes. tod-store waits tests (sweep); lifecycle tests (advance cancels); next_actor.rs (stale wait + NotStarted).

## 4. `working_in_cloud` infers "working" from the absence of a wait, contradicting the doc "Working is only ever what a live lease says"
Severity: wastes-time (misleading status)
Where: cloud_sync.rs:297 (`working_in_cloud`), :332 (`blocks_cloud_work` treats `You::NotStarted` as NOT blocking), doc comment "The supervisor reports no heartbeat, so this is derived" (stale: heartbeat exists, cloud_activity.rs). Consumers: unified/mod.rs:544 `apply_cloud_working` (feeds `cloud_working` into `apply_running_nodes`, so the "finished since you last looked" bookkeeping), app/window.rs:184 (close guard lists "X (state): running in the cloud").
Scenario: every cloud node with no pending wait/request, including one left stopped (finding 2), one whose supervisor ended on PrStuck (finding 1), or one sitting `idle`, is reported as "running in the cloud" in the close-the-app dialog and treated as lifecycle-running in the tree's bookkeeping. This is the literal "says working when nothing is happening".
Fix: delete the derivation. Use `next_actor::compute` standings: running = `NextActor::Working` only (which already covers `Work::Cloud` from the live heartbeat). The close guard should list `Working` nodes only and say "its supervisor is working".
Regression test: yes. cloud_sync/tests.rs:460 asserts the current behaviour ("assigned and waiting on nothing" counts as 2); invert it.

## 5. PR-state loop: PrStuck after 4 rounds is reachable in healthy runs; cloud polling is a full sandbox wake per minute; human-review wait wakes every 5 minutes day and night
Severity: wastes-time (cost) / blocks-work (PrStuck, see finding 1)
Where: mod.rs:671-815 (`babysit`), :794 (`waited_since` is a local variable: reset every wake, so `PR_SLOW_AFTER` never applies in the cloud); supervisor `Hook::at` (lib.rs ~l.196) returns "waiting: ..." for the poll wait that `record_poll_wait` just wrote (github_wait.rs `record_poll_wait`, due now+60s), so `sleep_watching` (mod.rs:880) stops the run at its first 500ms slice and the cloud "poll" becomes: schedule, sleep, wake, seed/pull replica, restore transcripts, run babysit, record, sleep (verify against the supervisor log: expect `wake scheduled` every ~60s during a bot/CI wait). `pr_review` human review: `wait_for_review` (mod.rs:817) uses `review_schedule`, whose defaults are 5 min both in and out of hours (settings.rs:255-260; doc says "seldom"); the orchestrator's `GithubGate` only absorbs `approved`/`merged`/`pr_draft` waits (github_gate.rs; `look_at_github` returns `NothingToWaitOn` for pr_review, github_wait.rs:178 area) and pokes the sandbox for pr_review, so a PR awaiting a human costs a sandbox wake every 5 minutes, 24/7.
`max_rounds: 4` (pr_readiness default, also the user's setting): rounds = Pr-agent turns since `pr_turns_base` (mod.rs:760). A healthy PR on a busy main burns rounds on `Work::Behind` (merge main again), failing flake, thread answers, review comments; four is easy. At the cap: `NeedsHuman::PrStuck` (plain words: "N rounds of fixing and reviewing and the pull request still is not clear") but invisible in the cloud (finding 1) and not resumable there.
`unchanged >= 2` (mod.rs:774) uses a fingerprint of head sha, mergeable_state, comment count and open thread ids (pr_readiness.rs:1258): it ignores `checks` and review state, so two turns that only re-ran/fixed CI without a push or comment read as "changed nothing twice" and stop the PR (false PrStuck).
Fix: (a) in the cloud do not "poll" at 60s: derive the wake time for `BotReview`/`ChecksRunning` from the wait cadence (checks ~2-5 min while running, bot ~ `rerun_after_minutes`), persist `waited_since` (e.g. the wait row's `created_at`) so the slow factor applies; (b) extend `GithubGate` to read-and-absorb `pr_review` waits (it already calls `check_github`; add a `pr_review` arm reading the same snapshot) so a human-review wait does not wake the sandbox; make `review_schedule` off-hours default hours, not 5 min; (c) add `checks` and `human_review` to the fingerprint; (d) count a round only when the turn pushed or posted something, and make `max_rounds` default 6-8 or "rounds without improvement"; (e) cloud-visible PrStuck (finding 1) plus a "Allow N more rounds" button that calls `renew_budget`.
Regression test: yes for fingerprint and rounds (pr_readiness tests, autopilot/tests.rs which already fakes the feed via `set_feed_override`); wake cadence via a supervisor test with a fake scheduler.

## 6. `bots: []` with a project skill that asks Greptile: the app does not wait for, require or count that review
Severity: wastes-time / correctness
Where: pr_readiness.rs:260-300 (`Assessment::of` builds `bots` only from settings), :302 `work`/`waits` (no `BotReviewMissing`, no `Wait::BotReview` with an empty list); gate/derived.rs `readiness_outcome` (ReviewCurrent/ReviewScore loop over `a.bots`, so with none they pass vacuously: "every review bot has reviewed the current head" with zero bots); doc pr-readiness.md ("Nothing is required: with no configuration...").
Trace: bots empty => the project skill (run by the PR agent) pushes fixes and posts "@greptile review"; the babysitter then reads the PR: threads answered/resolved, checks green or pending, `bots` empty so no bot wait. If checks are green it is `Next::Clear` => the `pr_draft`/`pr_review` loop returns to the gate, `pr-approved.review-current` and `.review-score` pass vacuously, and the node proceeds (to pr_review, or on to wait for a person) before Greptile has looked at the new head. With checks pending it waits only on checks. Greptile's inline comments, when they arrive, are `open_threads`, so they are handled; its summary score is never read, and a low score never produces work. Conversely, once a bot IS configured, `Wait::BotReview` has no deadline by design (doc: "no time limit while healthy") but `BotReviewMissing` goes to the agent once per `rerun_after_minutes` and each such turn is a round, so "bot never comes" ends as PrStuck after 4 rounds (finding 5; invisible in cloud).
What the 2026-11-02 churn shows: ed88f0fa/d58157af only change the wording of `render_work` for `Work::BotReviewMissing`; they cannot change behaviour for an empty bot list because that work item is never produced. The unsettled design question is who owns "ask the bot for a re-review after a push": the skill (agent) or the app. With the app unaware, there is no deterministic "bot reviewed the head" check at all.
Human review wait with nobody asked: in `pr_review`, `waits()` yields `Wait::HumanReview` whenever `mergeable_state == blocked` and no human approval, which also covers "blocked" for reasons no person can fix (required check missing, merge queue, CODEOWNERS), and `wait_for_review` then waits forever (`Others: a person's review`, `who` None when `requested_reviewers` is empty, next_actor.rs `external_wait`). `pr_draft` guards this with the `reviewer-assigned` criterion; `pr_review` has none, and nothing escalates.
Fix: (a) if the project skill asks a bot, the project should list the bot; make that a startup/setting-time check ("pr_readiness.bots is empty but the pr_draft skill mentions 'greptile'": show a notice in Settings and the node's PR panel), or move the "ask for review" into the app as `Work::BotReviewMissing` with a deterministic comment (settles the churn). (b) `Next::Clear` with zero bots must not claim "every review bot has reviewed"; make the criterion detail say "no review bots configured". (c) In `pr_review`, when `Wait::HumanReview` has no requested reviewer and no review for N hours, produce a `You` standing ("nobody has been asked to review") and a `Work` for the agent to request one per project skill.
Regression test: yes. pr_readiness.rs tests (empty bots with stale head), gate/derived.rs tests (zero-bot detail text), autopilot/tests.rs for the human-review wait escalation.

## 7. Budget: 30 sessions / 8 awake hours per node for its whole life; ordinary tickets can hit it; the question does not say what "Keep going" grants
Severity: wastes-time (and blocks-work while unanswered)
Where: mod.rs:70 (`Budget::default`: 30 sessions, 8h of awake time, not configurable: tod-supervisor main.rs:133, agentd runners.rs:492); `converse` increments `sessions` for every conversation started or reopened (mod.rs:939), including each `OnFailure::Retry` loop iteration (lib.rs ~l.378), each babysit round and each phase+evaluator pair; state is never reset by lifecycle moves; supervisor lib.rs:230 `budget_question`; answers.rs `granted` (each "Keep going" adds one more full budget: x2, x3...).
Counting a healthy ticket (rough): proposed 2 (phase + evaluator), design 2, planning 2, active 1-3, verifying 1-2, review 1 + fix 1-2, pr 1, pr_draft 1 + rounds, pr_review rounds, merged 2, released 2, learn 2 => about 20-25 with no rejection. Each evaluator rejection adds 2, each verify-fail loop (FixFailed -> Implement -> Verify -> Review -> Fix) adds about 4, each PR round 1. A day of work with a couple of loops reaches 30; 8 awake hours is about 20 agent turns of 25 minutes. Mid-turn time exhaustion also cancels the turn in flight (mod.rs:1021) rather than stopping at a boundary.
Wording: "This node has spent its budget (31 agent sessions) without finishing. Keep going?" with options "Keep going" / "Leave it stopped" (stop_questions.rs). It does not say the limit (30), that "Keep going" grants another 30 sessions and 8 hours (not unlimited), what the node was doing, or what "Leave it stopped" does (finding 2). The failures question reads "The agent failed N times in a row, most recently: <error>. Keep going?".
Fix: raise defaults (e.g. 60 sessions / 16h) or count only "agent turns that changed something"; make Budget a setting (settings.rs) read by the supervisor via `supervisor_settings`; state it in the question: "Used 30 of 30 sessions (8.0 of 8 h). Keep going gives it 30 more sessions and 8 more hours. Leave it stopped keeps it stopped until you change this answer." Show sessions/time used on the task panel for any node with a run.
Regression test: yes; supervisor tests/answers.rs for grants; `budget_question` string test.

## 8. No cycle detection: the lifecycle can ping-pong until the whole budget is spent
Severity: wastes-time
Where: mod.rs:432-438 (`NoProgress` only compares the current Standing+step with the immediately preceding one), lifecycle_next.rs (`FixFailed` reverts to `active`), conversation/phase.rs/phase.rs `is_stuck` (only the *same digest* rejected twice).
Scenario: verify fails -> `FixFailed` -> Implement -> Verify fails the same obligation -> repeat: every cycle changes the Standing, so no stop until 30 sessions or 8 hours; likewise evaluator rejects with small phase edits each time (no cap on rejections). Real money and a day of wall clock before a human hears of it, and the question then is the generic budget one.
Fix: in `run_with` count `FixFailed` reverts per stay and per obligation (store in `AutopilotState`), and stop with a specific `NeedsHuman::Looping { what: "verification failed the same obligation 3 times" }`; cap evaluator rejections per stay (3) with `EvaluationStuck`.
Regression test: yes, autopilot/tests.rs (scripted agent).

## 9. Protocol-level caps: what happens, and whether it reaches the user
Severity: cosmetic / wastes-time
All looping protocols share `CONTINUATION_CAP = 10` and `cap_or_stall` (conversation/protocol.rs:94-126) used by phase, evaluate, implement, verify, review, fix and pr (pr only in `pr` state; babysitting uses the autopilot's own rounds). At the cap or a no-change turn the driver emits `TurnFinished { error: None }` and records the `Stop` only in the journey (driver.rs ~l.870); the user sees nothing. The autopilot then re-decides from the store: if the Standing changed it starts a new conversation (a session is spent, so Implement on a plan of N steps needs about N/11 sessions); if not it stops with `NeedsHuman::NoProgress { step }` ("<step> changed nothing", internal names; local runs show it as a red "stopped"; cloud runs show nothing, finding 1).
Healthy-run risk: a large plan does NOT hit a hard stop (it costs sessions; 25 steps at one step per turn is 3 sessions), so the cap is not the problem; the problem is that the cap and its reason are mute and that `progress` for implement counts worktree dirt (`worktree_fingerprint`), so "progress" per turn can be real while the Standing-level check (step counts) says none => premature `NoProgress` after the first session if only statuses moved in ways the counts do not show. d9b2713c (phase `ready` is not progress, phase.rs marker excludes `ready`) is coherent with the Standing check: `Work -> Evaluate` changes `phase`, so no false NoProgress; stuck evaluations end `EvaluationStuck` (plain words, includes the fixes).
Table of per-protocol terminal reasons at the autopilot level:
- phase / evaluate: no change => `NoProgress { "phase" | "evaluate" }`; same rejection twice => `EvaluationStuck` (is_request false => shown as `Stopped` locally); pending decision from that conversation => hand back.
- implement: open steps => continue; all closed + this turn's green test run => done; only partial/blocked left => hand back to user (plan step attention item, visible); cap => new session or `NoProgress`.
- verify: done when every obligation/step has a verdict and this turn recorded a test run (red allowed).
- review: done when the review is recorded done; fix: no open finding and a green run in this turn.
- pr (state `pr`): certified phase, else `PrBlocked { why }` or `NoProgress { "pr" }`; babysit: `PrStuck { why }` (thread rounds >= 3 or turns >= 4 or two unchanged), `PrBlocked`.
A turn that finishes the work but records its test run in an earlier turn is "not done" (implement.rs next, fix.rs next): another continuation is sent even though nothing is left (cost, not correctness).
Fix: record each `Stop` as a conversation turn (`TurnRole::Notice`) and surface the last one in the task panel runner line; reword `NoProgress` to "the <plain name of step> ended without changing anything the next step needs".
Regression test: yes (protocol tests exist: implement.rs ~l.1065, verify.rs ~l.494, fix.rs ~l.364).

## 10. Lost-sandbox node with a pending decision (bom-upload-creates-duplicate-org-parts-2): shown, but answering does nothing and says nothing
Severity: wastes-time
Where: orchestrator answers.rs:`poke` -> wakes.rs:234 `poke_now` -> `RelayPoker::poke` returns `SandboxGone` => `report_lost` only; cloud_sync.rs:260 `cloud_status` (Deleted); task.rs:737 (lost: primary "Run in the cloud", menu "Stop running in the cloud"); next_actor.rs:379 (lost rows are NOT excluded from the local-file read, so a stale local autopilot file can speak for them).

Answering it is stored, synced, the orchestrator's poke finds the sandbox gone and drops it; the app does not repair (deleted_by_user is honoured, refresh.rs:112, lost.rs `any_marked`), so the answer takes effect only when the user later clicks Run in the cloud (which makes a new sandbox, and the new supervisor reads the answer). Regression test: yes, next_actor.rs with a cloud row `lost_at` set.

## 11. The standing is only recomputed on store changes; time-derived states can stay stale on a quiet store
Severity: wastes-time (verify)
Where: unified/mod.rs:439 (`rx.recv().await` blocks until the next fleet change; no timer) feeding `attention_feed::compute`; derived-by-time states: lease stale (activity.rs:34, 20s), beat stale (cloud_activity.rs:41, 60s), `overdue`, deferral expiry.
Scenario: the supervisor dies mid-turn; no new rows arrive, so no change event fires; the tree keeps showing Working until something else touches the store. Local lease heartbeats are direct writes (activity.rs:129) and may or may not emit; the daemon's reconcile ticks, the UI's does not. Verify by killing a supervisor and watching the glyph with no other activity.
Fix: in the poll loop `select!` on the change receiver and a timer set to the earliest time any input flips (`min(lease.heartbeat+STALE, beat.heartbeat+STALE, wait.due+grace)`), minimum 15s.
Regression test: logic yes (pure "next flip time" function next to `derive`); UI loop manual.

## 12. Timing constants: mostly consistent, three gaps
Severity: cosmetic / wastes-time
- Local lease: beat 5s, stale 20s (activity.rs:32-34): 4 beats. Cloud beat: 15s, stale 60s (cloud_activity.rs:37-41): 4 beats. Orchestrator fallback pull 20s (cloud_notify.rs:54; notices are the fast path, degraded 5s). Worst case age at the app = 15 + 20 + sync time, about 36-40s, leaving about 20s of clock skew tolerance before a live supervisor is shown "stopped responding". `CLOCK_SKEW_MS` is 30s (cloud_sync.rs:1596) so the two skew assumptions disagree (the heard check tolerates 30s; the stale check only about 20s).
- GAP A: `beat_once` and `Hook::at` take the same replica mutex; `at` does push+pull over HTTP with up to 6 attempts and 300s timeouts (orchestrator.rs:41, :70-117) while holding it, so a slow orchestrator can stall the heartbeat past 60s and a live supervisor is reported lost (`YouReason::Failed "cloud supervisor stopped responding"`). Fix: heartbeat on its own connection/thread without the replica lock, or shorten the HTTP timeout for sync calls.
- GAP B: `SUPERVISOR_REPORTS_WITHIN` = 150s covers sandbox boot + replica seed + transcript restore, but the first heartbeat starts only after `restore agent transcripts` (lib.rs `phase("first heartbeat")` after restore). A large transcript set eats the 150s with no beat; the user then sees the "has not reported in" failure for a healthy start. Fix: write a `starting` beat first thing after `HoldGuard::take`.
- GAP C: hang guard is 15 min with no activity (guard.rs:40, :344) and a long silent tool call (a 20-minute test run) counts as no activity: a healthy turn is cancelled and retried (each retry spends a session). Fix: treat a `Tool` part still `in_progress` as activity, or make it configurable (`TOD_HANG_MINUTES` exists, default not raised).
- `overdue` grace = 2x the wait's own deadline gap (finding 3); `OVERDUE_GRACE_MS` 2 min.
- Cloud `waited_since`/slow-poll factor never engages (finding 5).

## 13. Where "working" is inferred without a fresh lease/heartbeat, and where the user must click to unstick
Inferred working: (1) `working_in_cloud` (finding 4); (2) `Work::Cloud` = a live heartbeat only proves the supervisor process is alive, including during an agent hang up to 15 min and the supervisor's pre-run/replica phases; (3) the tree's `last_lifecycle_running` bookkeeping now includes the cloud set (unified/mod.rs:560); (4) `RunnerAction::Pause` appears from `runners.is_running`, a local fact (fine). Everything else routes through `NextActor::Working`, which requires a live lease or beat.
Clicks that should not be needed:
- Sync now / Check now / Reinstall to learn the outcome of a wake: needed because the supervisor's outcome is not synced (finding 1); Check now is not even offered in `pr_review` (task.rs:248, only pr_draft/approved/merged), where the babysitter's only look is the 5-minute wake.
- Re-answering the stop question to resume (finding 2); no Resume for cloud nodes at all (no `ResumeFreshBudget` in the cloud branch, task.rs:737-775).
- Run in the cloud after a deleted/lost sandbox (intentional, but the answer path does not tell the user).
- Local daemon only: `start_due` (agentd runners.rs ~l.252-275) resumes a request-stopped node only if it saw it waiting in this process (`seen_waiting`); a daemon restart between the ask and the answer leaves the node `NotStarted` until the user starts it.

## 14. Rendering table: Outcome / NeedsHuman -> task panel / tree glyph
Local runs (cloud runs: none of these, see finding 1). `outcome_reason` (next_actor.rs:604), `standing.rs`.
- `Done` -> none (node is done). `Waiting` -> none; the node's waits give `Others` (diamond, red if overdue, amber if retrying).
- `Stopped` by Pause/Stop now -> `You: Paused`, blue triangle (same glyph as NotStarted and Request; not distinguishable). Other `Stopped` -> `You: Stopped`, red triangle + cross, runner line "stopped" + reason (a `failed: ` prefix -> `Failed`).
- `BudgetExhausted` -> `You: Stopped "budget spent: N sessions" / "budget spent: Xh of work"`, red; local buttons "Resume with a fresh budget". Cloud: a decision (finding 7).
- `NeedsHuman::Decision | BlockedSteps` (requests) -> hidden once the item is answered; then the node falls to `NotStarted` until something restarts the runner. `FailingCriteria | GateNotPassed` -> same, but there is never an attention item (finding 1), so always `NotStarted`.
- `AgentFailed` -> `You: Failed "<error>"`, red. `NoPlan`, `EvaluationStuck`, `PrBlocked`, `PrStuck`, `Permission`, `NoProgress` -> `You: Stopped "<describe()>"`, red; plain English except `NoProgress` (internal step names) and `NoPlan` ("no plan steps to implement": says nothing about what to do).

## 15. Derived differently by the app, the daemon and the orchestrator
- Who is next: app and daemon share `next_actor::compute`, but the orchestrator has no equivalent: its `GithubGate` decides "still waiting vs poke" from `check_github` for the *current lifecycle* only (pr_review waits poke; stale waits poke dead sandboxes).
- "Waiting": supervisor `waits::check` (any pending wait stops the run), `next_actor` (waits rank below requests, above NotStarted), `runner_status::github_wait` (soonest `github:` wait only), orchestrator gate (`github:` events only). Four readers, four rules; nothing normalises spec spelling (`github:pr 2810 checks` vs `github:pr:2810:checks`: `WaitKind::from_spec` classifies the space form as `Other`; webhooks accept both).
- "Is it in the cloud": `next_actor` uses `lost_at.is_none()`; `cloud_status` and the panel add `deleted_by_user` from a JSON file the orchestrator cannot see; `working_in_cloud` uses `lost_at.is_none()`.
- Budget/stop answers: the supervisor reads `stop_questions::latest`; the app never does.

## Design changes that remove whole classes of failure
1. One synced `run_state` per node written by whoever runs it (supervisor or local): `{ phase: working|waiting|stopped|done, reason_kind, reason_text, since, resumable_by }`, replacing the idle heartbeat's bare "idle" and the private autopilot JSON. `next_actor` reads it for cloud and local alike; every stop (including PrStuck, NoProgress, LeftStopped) must set it, enforced by the `Outcome` -> state mapping being exhaustive. Removes findings 1, 2, 10 and the "not started" lie.
2. Waits owned by lifecycle stays: record the stay id on each wait and cancel/expire all pending waits when the stay ends; give `next_actor` an authoritative `expired` check so a past-due wait is a fault, never `Others`. Removes finding 3 and the stale-wake class.
3. Stop questions become the one resume mechanism: every non-request stop files (or updates) a single "stopped: why / Keep going" decision on the node, the answer is the only thing the supervisor and the app consult, and any explicit user action (Run with a new session, Sync, new context) supersedes an older "leave stopped". Removes findings 1, 2 and the budget dead ends.
4. Delete derived "working" everywhere except `NextActor::Working` (lease or beat), and make the heartbeat carry the activity ("polling GitHub", "agent turn", "sleeping 5 min") so the panel can distinguish an agent turn from a poll.
5. A cloud wait is a scheduled wake, never an in-process poll: compute its time from the wait cadence per kind, absorb every GitHub wait (including pr_review) in the orchestrator gate, and give each wait kind an explicit give-up behaviour (expire -> `You` with the reason).
6. Counters that exist to catch loops (sessions, rounds, rejections, fix cycles) live in one `AutopilotState` section the app can show and renew from either place, with a cycle detector keyed on (state, failing obligation/criterion).
