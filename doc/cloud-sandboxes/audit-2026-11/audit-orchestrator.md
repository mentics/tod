### A3. "The orchestrator is out of date"

What decides it:
- `scripts/lib/stamp.sh: sandbox_source_hash` hashes Cargo.toml, **Cargo.lock**, `.cargo`, assets/sandbox, build script, and **every file** (src, tests, comments) of every workspace crate any of tod-relay, tod-supervisor, tod-orchestrator, tod-cli, tod-watchdog depends on: agent, agentd-client, cli, core, integration, journey, orchestrator, problems, relay, sandbox, store, supervisor. That is nearly everything except tod-ui. One hash covers 5 binaries and 2 deployables (orchestrator + watchdog job).
- `build.sh` compares it to `<data root>/orchestrator-deployed.hash` (live: `30edadedb80fa7c9 f6ca8ff0 main`) and only prints "out of date". `deploy.sh` redeploys. `deploy::ensure_orchestrator` (cloud_sync/deploy.rs) never redeploys an existing one.
- There is **no runtime check at all**. grep finds no build stamp, protocol number or `user_version` anywhere in tod-orchestrator, cloud_sync.rs or tod-supervisor. `/health` returns `ok`. The only detector is `older_orchestrator_hint` (cloud_sync.rs:1682), which pattern-matches the text "CHECK constraint failed|no such column|no such table" in a failed `send` (not in a failed feed apply, not in a seed).

Does a tod-store migration force a redeploy? Yes, hard, even when the orchestrator's own code is unchanged, because the orchestrator opens the user's database with its own `FleetStore::open`:
- App newer than orchestrator (schema newer): `apply_migrations` refuses a database whose `user_version` is newer (fleet/schema.rs:107-112). A seed from the app then destroys the orchestrator's database (finding 3). Without a seed, a new CHECK value or column the old binary lacks makes every `POST /changes` carrying such a row fail (live: 215 x `CHECK constraint failed: capability IN (...)` 500s on Oct 19 16:54-17:25).
- Orchestrator newer than app/daemon: the feed brings values the local CHECK rejects and the app's whole apply fails forever (live: tod-live-verify daemon, "14104 failures in a row", `CHECK constraint failed: state IN ('proposed',...,'done')`, finding 1).
- Node sandboxes are reinstalled on every build (`cloud-install-stamps.json`, refresh.rs) while the orchestrator is not, so supervisor/tod-cli and orchestrator skew by construction after any rebuild.

Proposal (finding 3 and finding 19): replace the source hash by an explicit compatibility contract: `GET /health` returns `{wire: N, schema: user_version, build: stamp}`; every client (app, daemon, supervisor) sends its own on each request (`X-Tod-Wire`, `X-Tod-Schema`); the orchestrator answers 426 with the exact fix when the client is newer, and clients refuse to apply feeds from a newer schema with a clear error. Bump `wire` only when the sync protocol changes; schema skew is handled by making migrations additive (below). Redeploy the orchestrator only when `schema` or `wire` increases or its own crate (tod-orchestrator + the sync/impact/webhook code it uses) changed, hashing only those crates' `src/` (not tests, not Cargo.lock beyond its own dependency closure). The app already deploys when none exists; add "deploy when /health says wire/schema is lower than mine and no node is mid-turn" (a rolling restart of the orchestrator process takes the sandbox and /data intact; `tod-sandbox orchestrator` already uploads binaries and restarts).

### A4. Seed / reseed protocol and where parties disagree

Protocol as coded:
- Orchestrator: `POST /users/<u>/seed` closes the user's store (409 if a request holds it, `users.rs:67 close_if_idle`), copies the snapshot over `tod.db`, reopens (migrating), then writes `orchestrator-seed-seq` (= snapshot last_seq, the feed floor) and then `orchestrator-seed-id` (new uuid) (sync_backend.rs:60-80). `is_seeded` = the seq file exists (sync_backend.rs:52). Unseeded users get 409 `NOT_SEEDED` on changes/feed.
- App: `sync_once` (cloud_sync.rs:718): if `state.seeded`, asks the feed for `seed_id` (`pull(i64::MAX)`, line 729); a different non-null id means the database was replaced: it pulls `after=0` (which is only the changes since the other seeding, because the feed never goes below seed_seq), applies them, sets `seeded=false`, and seeds the orchestrator with its OWN database. `NOT_SEEDED` does the same (cloud_sync.rs:696). The 409 retry is 5 attempts at 0.5-2 s (cloud_sync.rs ~595).
- Supervisor: `Replica::open` (replica.rs:84) pulls `i64::MAX` for the seed id, and if it differs from its saved id it DELETES its copy and downloads `/snapshot`; `pull` (replica.rs:214) bails mid-run when the id changes ("the next start takes a new copy").
Disagreements and silent losses: finding 2 (two data roots fight), finding 9 (non-atomic seed files, `(None,Some)` adoption, `(Some,None)` mismatch, supervisor's pushes into a reseeded history, discarded conflicts, window loss).

### A5. `sync_changes` size and pruning

Never pruned: no `DELETE FROM sync_changes` exists anywhere in the repo (grep across crates). Live measurement (`sqlite3 -readonly ~/.config/tod/tod.db`): `tod.db` = 338 MB; the `sync_changes` table and its index = **248 MB (75%)** (dbstat); 44,588 rows (seq 1..44588 = `sent_after`, so none were ever deleted, even though every row is long acknowledged). Of that, `tbl='conversations'`: 5,665 log entries holding **219 MB** of `old_row` (avg 39 KB), because `conversations.opening_context` (up to 96 KB) is copied whole into `old_row` on every UPDATE of the row (each turn bumps `updated_at`). The live-verify copy: 3,866 rows. `feed_after: 57612` is the orchestrator's log head, whose own log is unmeasured but fed by `apply_changes_from`, which logs each change again, and by `conversation_live` (finding 6).
Yes, the snapshot is sent in full on every reseed: `sync_once` does `sync::snapshot` then `std::fs::read(&tmp)` and one POST (cloud_sync.rs ~756-765), 338 MB, including the 248 MB of log that the orchestrator immediately declares dead (it sets the feed floor to the snapshot's last_seq, so none of those rows can ever be served). Each supervisor first start (`GET /snapshot`) downloads the orchestrator's whole database, log included, into memory (`std::fs::read`, sync_backend.rs:156-170) with 300 s timeout and 6 retries. Finding 6.

### A6. Can a change never be pulled?

Yes, four ways (finding 8): (1) a failed non-429 ntfy publish is consumed as "announced"; (2) `cloud-sync.json` caches the ntfy topic forever and live evidence shows two data roots of the same user on the same orchestrator hold DIFFERENT topics (`tod-01e5...` vs `tod-c104...`), so at least one is subscribed to a dead topic; (3) the 20 s fallback poll exists only while some `cloud_nodes` row has `lost_at IS NULL`, and `retire_done` removes the row when a node reaches done; (4) an orchestrator restart resets the notifier's baseline, so a decision pending at that moment is never alerted to the phone.

## Part B. Findings, most severe first

### 1. One rejected row wedges sync in both directions, forever, silently
Severity: blocks-work.
Where: cloud_sync.rs:718-830 (`sync_once`), tod-store/src/sync/mod.rs:510-600 (`apply_changes_with`, one transaction for the whole batch), orchestrator sync_backend.rs:89-130, cloud_sync.rs:1682.
Scenario: any single change that the receiving schema rejects (a CHECK value, a missing column, FK) aborts the entire batch. Send direction: the orchestrator returns 500 with SQLite's text, the cursor `sent_after` never moves, every later user edit is stuck behind it, and the app retries every 5-20 s. Receive direction: `sync::apply_changes` fails, `feed_after` never advances, same.
Evidence: agentd.log lines 2798-3230 (Oct 19 16:54-17:25): 215 x `orchestrator changes: 500 ... CHECK constraint failed: capability IN ('spec', 'lifecycle', ..., 'lifecycle_config')`. Today: `~/.local/share/tod-live-verify/daemon/agentd.log` last line: `cloud sync still failing (14104 failures in a row ...): CHECK constraint failed: state IN ('proposed','design',...,'done')` (a lifecycle state this old daemon's schema lacks, delivered by the feed). 14,104 failed syncs x 3 HTTP requests each against a shared, billed orchestrator. The hint `older_orchestrator_hint` only wraps `send` errors, only as log text; the user sees nothing in the UI (WARN in the log panel at most, repeats suppressed to one per 5 minutes by `FailureLog`).
Fix: (a) apply row by row inside SAVEPOINTs in `apply_changes_with`; a row that fails is written to a new `sync_rejected(direction, table, key, error, change_json)` table, reported in `ApplyReport::rejected`, and the cursor moves on. (b) Make the orchestrator answer a malformed or rejected batch with a 4xx (422) that names the first bad row, so the supervisor stops retrying 6 times (orchestrator/src/lib.rs:150-163 currently makes it 500, reports it as a problem and pokes the notifier, which then makes the app sync again: a feedback loop, finding 12). (c) `sync_once` surfaces `rejected > 0` as an ERROR-level log (toast) with the table/key/text and "orchestrator is older/newer than this app" decided from the wire/schema contract (A3), not by string matching. (d) Skip `retry` for the whole sync when the same error repeats N times: back off exponentially instead of every 5-20 s.
Test: yes. `crates/tod-store/src/sync/tests.rs`: a Change whose `after` violates a CHECK; assert the other changes apply and the bad one is reported. `crates/tod-core/src/cloud_sync/tests.rs` (the harness `start_orchestrator` exists): assert the cursor advances past it.

### 2. Any second data root for the same user silently takes over (and wipes) the orchestrator's database
Severity: blocks-work (data loss).
Where: cloud_sync.rs:729-760 (reseed), cloud_sync.rs:696 (`NOT_SEEDED`), sync_backend.rs:60 (`seed_inner` has no guard), test cloud_sync/tests.rs:584 `an_orchestrator_seeded_by_another_copy_is_seeded_with_this_one_again` pins the behaviour as intended.
Scenario: the orchestrator is one database per `X-Tod-User`, and the user name comes from `sandboxes.toml owner` (cloud_sync.rs `resolve`). Every data root with the same owner and orchestrator shares that one database, whatever `client_id` it has. Live: `~/.config/tod` (seed_id ed22a673..., sent 44588, feed 57612) and `~/.local/share/tod-live-verify` (no seed_id, sent 3866, feed 44585) both sync `https://sbx-tod-orchestrator-budku6...` as `jshellman`. When a root finds `known != now` it takes only the changes since the other seeding (the other root's baseline content is NOT fetched, the feed floor is the seed point), then re-seeds the orchestrator with its own database. Roots A and B alternate forever, each time uploading a full snapshot (338 MB), replacing the other's nodes, and every running supervisor either aborts its run at the next boundary ("seeded again", replica.rs:214) or takes a new copy and loses unpushed writes.
Also: the tod-live-verify root has `seed_id` absent, so `(None, Some(now))` (cloud_sync.rs:~747) adopts the current id as if its copy had come from it, with a `feed_after` that belongs to another numbering.
Evidence: above state files; the test file.
Fix: scope the orchestrator database by (user, data-root identity) when seeding: the seed carries the app's persistent `client_id`/a stable `workspace_id` generated at first seed and stored in the orchestrator next to `seed-id`; a seed from a different `workspace_id` onto a seeded user is refused with 409 `owned by another data root <id>; use --force-adopt` unless `force=1`. The app then reports a clear error ("this orchestrator user already holds data root X; set a different `user` in cloud-sync.json or adopt it") instead of reseeding. In `sync_once` replace `known != now => seed ours` by: pull the orchestrator's `/snapshot` and replace the local database only after confirmation, or refuse. Also require `seeded=false` seeding to compare `last_seq` of the orchestrator DB: do not overwrite a database that has changes the seeder has not pulled (check `feed.last_seq > state.feed_after` before overwriting; if so, pull first, and seed only the delta).
Test: yes, extend `cloud_sync/tests.rs:584`: two apps, assert the second seed is refused and neither database is lost.

### 3. A schema newer than the orchestrator build destroys its database on seed and turns every route into a 500
Severity: blocks-work.
Where: sync_backend.rs:60-80 (`seed_inner`: `sync::restore` happens before `users.get`), fleet/schema.rs:107-112 (refuses newer `user_version`), no handshake (A3).
Scenario: the app (schema N+1) seeds an orchestrator built at N (needed after a volume loss, NOT_SEEDED, or the first seed). `restore` overwrites `tod.db` with the N+1 snapshot, then `users.get` fails with "fleet database user_version N+1 is newer than supported N" and the handler returns 500, before the seed files are rewritten. The previous `orchestrator-seed-seq` still exists, so `is_seeded` is still true: every later `/changes`, `/cli`, `/snapshot`, webhook and notifier probe fails 500 for that user, and the old database is gone. All running agents' `tod-cli` calls fail. Each 500 also writes a problem and pokes the notifier (finding 12).
Fix: in `seed_inner` peek the snapshot's `user_version` (`schema::peek_user_version`, schema.rs:56) before touching the live file and reply 426 with both versions; restore into `seed-incoming.db`, open it with the migration, then rename it over `tod.db` (keep the old file as `tod.db.pre-seed` until the next successful request); delete `orchestrator-seed-seq` first and rewrite seq+id in a single `orchestrator-seed.json` via write-and-rename. Add `/health` version fields (A3).
Test: yes, `crates/tod-orchestrator/tests/http.rs`: seed with a snapshot whose `user_version` is bumped, assert 426 and that the old database still serves.

### 4. Pokes run synchronously inside the request that triggers them
Severity: blocks-work (timeouts, retries, 409s).
Where: sync_backend.rs:127-129 (`impact_handler::poke`, `answers::poke`, `wait_changes::poke`) run before the response is written; `Wakes::poke_now` (wakes.rs:234) calls `RelayPoker::poke`, which does a Blaxel `get` and a `POST /poke`, each with 15 s connect and 60 s global timeouts, serially per node; webhooks.rs:448-495 `route_user` and `poke_now`.
Scenario: a supervisor or the app pushes changes that affect N running nodes. The HTTP reply waits for N sequential Blaxel lookups plus relay pokes; a node whose sandbox is in standby or slow costs up to 75 s. The pusher sees `timeout: global` or the supervisor's 6 retries, re-sends the same batch (already applied, so each retry re-pokes), and `Arc<UserData>` is held the whole time, so `close_if_idle` returns false and the app's seed gets 409 (the app retries 5 times over 5 s only, and the 409 comes after the whole 338 MB body was uploaded, finding 16). GitHub's webhook delivery times out at 10 s the same way (the event is processed, but GitHub marks the delivery failed and never retries).
Evidence: code. Live: `timeout: global`, `502`, `reset` are the three most frequent lines in the daemon log. The orchestrator's own stderr is not readable from here (unverified), but the structure makes it certain.
Fix: make pokes a queue: `poke_now` pushes `Wake{at:0}` into `Wakes` and notifies the timer's condvar (it already exists, wakes.rs `changed`); a small pool of poker threads (4) does the Blaxel lookup and POST with its own timeout, per sandbox with no head-of-line blocking. Handlers return as soon as the DB commit is done. Webhook responses return after recording and queueing.
Test: yes, wakes.rs tests have `FakePoker`: add a poker that sleeps; assert `apply_changes` returns before it completes (`tests/impact.rs`, `tests/answers.rs` pattern).

### 5. The supervisor holds one mutex across all HTTP retries, and a transient orchestrator error aborts the run
Severity: blocks-work.
Where: tod-supervisor/src/replica.rs:249-272 (`push`), :214 (`pull`), :275-302 (`cloud_beat`), orchestrator.rs:69-124 (`request`: up to 6 attempts, 250 ms to 8 s backoff, each with a 300 s agent timeout), lib.rs:173-185 (`at`: `replica.push()?; replica.pull()?;`), lib.rs:301 (`pull()?`), lib.rs:454, beat.rs:30-100.
Scenario: `Arc<Mutex<Replica>>` is locked for the whole push/pull including every retry sleep and every request timeout (worst case 6 x 300 s). The heartbeat thread (`beat_once`, same mutex), the reply-in-flight writer and the boundary push all queue behind it. Heartbeat older than 60 s means the app shows the node as stopped/lost although it is working. At a step boundary a push or pull failure is returned with `?`: a 502 window of about 25 s (the retry budget) ends the autopilot run at that boundary. `Beating::start` fails the whole wake if the first beat cannot be sent. At the end of a wake `schedule(...)?` posts the wake once with a 30 s timeout and no retry (scheduler.rs:86-103): if that fails, the wake is never registered, the node sleeps with nothing to wake it, and the error is only forwarded to the orchestrator next time the supervisor talks to it, which is exactly what is failing (problems.md "Not covered").
Evidence: code. Unverified live (sandboxes not inspected).
Fix: release the replica lock while waiting on the network (take a copy of the changes under the lock, send without it, record the cursor under it); one overall deadline (e.g. 20 s) for beat and live-turn pushes (they are best effort); at boundaries retry with jittered backoff for up to ~3 minutes and then stop the run with a `NeedsHuman`-style failure naming the orchestrator error instead of aborting immediately; a wake that cannot reach the orchestrator exits non-zero WITH a local retry (the relay/scheduler re-pokes it after N seconds); `Scheduler::schedule` gets the same retry as `request`.
Test: yes with a fake orchestrator that blocks: `crates/tod-supervisor` has the replica tests; assert the heartbeat still fires while a push is blocked.

### 6. `sync_changes` is an unbounded 248 MB log that is shipped with every seed and snapshot
Severity: wastes-time, trending to blocks-work (338 MB seeds; memory).
Where: tod-store/src/sync/mod.rs:275-330 (`install`, trigger stores the full `old_row`), mod.rs (no prune), sync_backend.rs:156-170 and cloud_sync.rs ~756 (`std::fs::read` of the whole snapshot into memory, both sides), http.rs:95 (`vec![0; len]` allocates the declared Content-Length, up to 512 MB, BEFORE the body arrives), export_changes_for (mod.rs:443, no limit/paging).
Scenario: see A5. Additional: `conversation_live` is a synced table written every 3 s with the whole reply so far (conversation_live.rs; "reply in flight", autonomous-nodes.md): on the supervisor's copy each UPDATE logs the previous whole reply in `old_row`, and the orchestrator logs each pushed change again with `old_row`: quadratic growth per turn (unverified size). `node_events` (synced) stores the raw GitHub payload for every push/check event of a branch (webhooks.rs:448-470) and is never pruned. `GET /changes` has no page limit: a client that was away gets all rows in one JSON body under a 300 s timeout; a client that cannot download it in 300 s can never catch up. Memory: the orchestrator sandbox has 4 GB; a seed (body + file write), a snapshot (file + Vec) and a feed pull concurrently can approach it, and a 502/reset during one is the likely symptom.
Fix: (a) prune: after the app's `sent_after` is acknowledged, delete `sync_changes` rows <= min(all clients' cursors) on both sides (the orchestrator knows each client's pull cursor from its `after` params; keep a `client_cursors` table); (b) stop storing unchanged large columns in `old_row`: store a hash (or only changed columns) for `conversations.opening_context`, `conversation_live.parts`; exclude `conversation_live` from the log entirely and send it out of band (it is a cache); (c) a seed/snapshot VACUUMs the log out: `sync::snapshot` copies then `DELETE FROM sync_changes` in the copy (the receiver never reads it; the supervisor sets its cursor to the snapshot's last_seq, which is unchanged if the AUTOINCREMENT counter (sqlite_sequence) is preserved); (d) stream the body to disk in `read_request` (do not pre-allocate), reject bodies above a small limit on non-seed routes, and cap `GET /changes` at N rows or M MB returning `more:true`; (e) prune `node_events` to the last K per node.
Test: yes. `sync/tests.rs`: a prune function and an assertion that snapshot rows are 0 and `last_seq` is unchanged; `tests/http.rs`: a feed page limit.

### 7. Database broker: ownership is checked after everything else, `list` is unscoped, and the design broadcasts to unrelated daemons
Severity: wastes-time (agent gets wrong or no login; user has to answer a request).
Where: db_broker.rs:178-205 (`answer`: `list` at 181 and database-name lookup at 185 come BEFORE `sandbox_of(node).ok_or(NotMine)` at 191), broker.rs:61 (`connected`), broker.rs:196-221 (`next`/`reply`), broker.rs:206 (first non-`not_mine` reply wins), db_broker.rs:82 (`Quiet`), cloud_sync.rs:480,517,526.
How a client is identified: by `X-Tod-Client`, which is `client_id(root)` (`app-<12 hex>`, generated once and stored in that data root's cloud-sync.json, cloud_sync.rs:94). That is a data root, not a machine, and the orchestrator user is the `owner` name. So every data root of that owner, on any machine, is one more broker client (`seen` in broker.rs). The request is broadcast to all of them.
Why a daemon for another root answers: (1) `op:"list"` is answered by every daemon, the first reply wins, and an old daemon's list can differ; (2) the database name is validated before the node: a root that declares no database of that name (or fewer), or whose `sandboxes.toml` fails to parse, replies `{"ok":false,"error":"no database named ..."}` for a node it does not own, and that is a final error, not `not_mine`; (3) a daemon from a build before `NotMine` existed replies a final error for an unknown node (the live-verify daemon, Oct 29 build, is one); (4) all of them stay "connected" for 45 s after their last poll, so a daemon that is gone still gets requests, and a broker poll that hangs for the 300 s global timeout makes all of them look absent.
What should the design be: ownership by the orchestrator, not by daemons deciding. `cloud_nodes` is already a synced table written by the app that created the sandbox (the app that holds the tokens): add `owner_client` (that app's client_id) to the row. The broker then routes a node's request ONLY to its `owner_client`, and answers 503 naming that data root if it is not connected; no broadcast, no `not_mine`, no `list` collision. In the daemon, move the ownership check before everything (including `list`), make every non-ownership outcome `not_mine`, and treat a database name that is not declared as an error only for the owner. Separately, daemons must exit when they have no reason to live (item 18).
Also fix: `broker_next` needs its own timeout of `wait+10 s` instead of the 300 s global; wrap `broker_reply` in the gateway retry (the first answer wins, so a retry is safe; today a 502 on the reply makes the sandbox wait the full 90 s and fail "did not answer in time" after the token was already signed); `Quiet` must re-log after recovery and count occurrences; broker.rs should use the poison-tolerant `unwrap_or_else(|e| e.into_inner())` that the rest of the crate uses (4 places) and prune `seen`.
Test: yes. broker.rs unit tests already model multiple machines (`machine_replying`); add one where the non-owner declares a different database set and replies for `list` first. db_broker.rs tests: `answer` for an unknown node with an unknown database name must be `NotMine`.

### 8. Notices can be lost for good; the fallback poll can be off; the cached topic can be dead
Severity: blocks-work (a change never appears), plus a missed phone alert.
Where: notify.rs:407-450 (`try_announce`), :419 (`decide` marks the change as announced BEFORE the publish; only a 429 restores `seen`), :295 (`failure_to_report` says "it pulls on a timer until announcements work again"), cloud_notify.rs:97-125 (`any_running_in_cloud`, `spawn_fallback_poll`), :299-310 (`topics` returns the cached `state.notify` forever), :329.
Scenarios:
(a) ntfy answers 502/timeout/DNS to the orchestrator's publish: `seen.last_seq` is already updated, nothing is retried, the notice is gone. Only 429 sets `degraded_until`, so the feed does not tell the app to poll. The app polls every 20 s only while a `cloud_nodes` row with `lost_at IS NULL` exists. A change that arrives when no row exists (a node just retired by `retire_done` at the end of a sync, lost_at set while being replaced, the user's other data root) is never pulled until the next unrelated notice. The `NeedsYou` phone alert (`attention` set) is consumed the same way: never re-sent. The message the orchestrator reports ("pulls on a timer") is false in that case.
(b) The topic secret is stored per user in the orchestrator's `notify.json`; the app copies it into cloud-sync.json once. If the orchestrator's data is recreated (live: `orchestrator_volume` is NOT set in sandboxes.toml, so /data is the sandbox's own disk) the secret changes and the app stays subscribed to the old topic. Live: the two roots of user `jshellman` on one orchestrator hold different topics.
(c) After an orchestrator restart the notifier baseline is empty (`announced` is in memory): the first look sets `attention` as the baseline, so a decision pending at restart is never alerted.
(d) doc says "at most once a second" (orchestrator.md) but `MIN_INTERVAL` is 30 s (notify.rs:38): a burst after a quiet period shows up to 30 s late on the trailing edge.
(e) `ntfy.sh` per-IP limits are shared with other Blaxel tenants behind the same egress IP, so 429 will recur regardless of tod's rate. Every degraded minute costs 12 syncs x 3 requests.
Fix: in `try_announce` mark the observation as announced only after `publish` succeeds, and for any publish error (not only 429) set a `degraded_until` of 60 s and put it in the feed. In the app, poll while degraded OR while `last known degraded` OR for 5 minutes after any sync failure, and make `any_running_in_cloud` also true when any `waits` or `decisions` on a cloud node are pending, or simply always poll every 60 s while the app is open and seeded (3 small requests a minute is cheaper than a lost change). Re-fetch `GET /notify` on every seed_id change, on a subscribe error 404, and every hour, and compare. The more robust fix removes ntfy for the app: add `GET /users/<u>/changes?after=n&wait=25` (a long poll, like the broker's `next`) which the daemon already can hold; keep ntfy only for the phone alerts.
Test: yes. notify.rs tests have `Probe`/`Sink` fakes: a sink that fails once with a non-429 error must be retried; cloud_notify.rs tests have `poll_due`: extend with the cases above.

### 9. Reseed windows: non-atomic seed state, data loss during the upload, unseen conflicts, adoption disagreements
Severity: blocks-work (rare but silent).
Where: sync_backend.rs:60-80, :52, cloud_sync.rs:729-760, replica.rs:84-130,214-247,249-272, orchestrator.rs:141 (`push_changes` discards the `ApplyReport`).
1. `seed_inner` writes `orchestrator-seed-seq` and then `orchestrator-seed-id` as two files after the database was replaced. Between `restore` and those writes, `is_seeded` is true from the PREVIOUS seed and `export_changes` uses `after.max(old seed_seq)` against the NEW database's numbering: a supervisor pulling in the window gets thousands of the app's historic log rows applied to its copy and advances to the new `last_seq` under the OLD seed id (check passes). A crash between the two writes leaves seq without id (None): the app's `(Some(known), None)` falls into `_ => {}` and keeps going, the supervisor sees `Some != None` and re-copies: they disagree. `std::fs::write(SEED_ID_FILE)` failing returns 500 after the database was replaced.
2. Data loss window: `sync_once` pulls `after=0`, snapshots, then uploads 338 MB. Supervisors keep writing to the orchestrator for the whole upload (a `tod-cli` write from an agent, a push). The seed then replaces the database and every row written after the snapshot is gone, with the supervisor's `push_after` already advanced. Nothing quiesces the nodes.
3. `Replica::open` deletes its whole copy on a changed seed id although the comment says "Losing the copy loses nothing". Unpushed changes (the last `push` before the failure, the in-flight turn, lifecycle moves) are lost; and at a boundary `push()` runs BEFORE `pull()` (lib.rs:183-184), so the supervisor pushes its writes into the reseeded history, where `drop_orphans` (sync/mod.rs:695) silently deletes any row whose parent node is missing from the new seed and reports it only as `ApplyReport::conflicts`, which `Orchestrator::push_changes` throws away. The doc (autonomous-nodes.md "Conflicts") says conflicts are "recorded on the node, for the user and for that node's supervisor"; apply_changes returns the report and nothing records it anywhere. Rows from a supervisor win over a concurrent user edit ("the sender wins") with no trace.
4. `(None, Some(now))` adoption (cloud_sync.rs ~747) trusts an old copy (live-verify) as if it came from the current seeding.
Fix: write `orchestrator-seed.json {seq,id,workspace_id}` atomically, delete it before replacing the database, and make `is_seeded` mean "the file exists and the database's `last_seq >= seq`"; take `sync_lock` for the whole seed; make the app seed only when the orchestrator has no unpulled changes (`feed.last_seq == seed_seq` or pull them first and refuse if nodes are running without `--force`); `push_changes` returns the report and the supervisor logs each conflict at WARN (and the orchestrator records a `node_events`/problem row on the node for conflicts from a client other than the app); a supervisor that sees a changed seed id pushes nothing, writes its unpushed changes to `unpushed-<ts>.json`, then re-copies.
Test: yes. `tests/http.rs` `seed_*` and replica tests.

### 10. Wake timer: serial pokes, no panic guard, infinite silent retries, volatile state
Severity: wastes-time / blocks-work (nodes asleep forever).
Where: wakes.rs:191-232 (`fire_due`: serial, gate and poker inline), :248-270 (`run_timer`, `spawn_timer` has no catch_unwind or restart), :167 (`put` replaces by id only; `remove` checks user but `put` does not), :234.
Scenarios:
- Pokes are serial on one thread: three wakes whose sandboxes hang cost 3 x 75 s before the next wake fires; the GitHub gate (`check_github`) also runs on this thread.
- A panic in the timer thread (gate, store, poker) kills it silently: no wake ever fires again and `LocalRelayAwake::tick` stops renewing, so the orchestrator itself can go to standby and nothing in the app says so. All `rows.lock().unwrap()` calls then poison too.
- A poke that fails (missing `TOD_ORCHESTRATOR_BLAXEL_*` credentials, a standing 5xx) is retried every 60 s forever (`RETRY_MS`); the only report is `eprintln!` on the orchestrator's stderr (wakes.rs:213), which the app never reads (problems.md says its failures go to the log panel). Meanwhile the orchestrator holds itself awake (billing) for as long as any wake is pending.
- Wakes live in `<base>/wakes.json` on /data. Without `orchestrator_volume` (the live config) a recreated orchestrator has no wakes, and nothing re-registers them: a sleeping node's supervisor is not running, so it cannot re-post (unverified: I found no app-side reconcile of `waits` against the orchestrator's wakes).
- `put` replaces by wake id regardless of user: a collision across users overwrites another's wake (ids are wait uuids, so unlikely; it also means the `user` field can be spoofed by any sandbox that can reach the orchestrator, per the documented trust model).
Fix: move poking to a worker pool (finding 4); wrap the timer loop in `catch_unwind` with restart and record a problem; report a poke failing more than 3 times to the user's problem channel (`problems::report_own`) and give up after N hours by marking the node `lost`; have the app reconcile pending waits with `GET /wakes` after a NOT_SEEDED/reseed and when `/health` shows a new process start id; set `orchestrator_volume` by default when creating the orchestrator.
Test: yes (wakes.rs FakePoker tests): slow poker, panicking gate, repeated failure.

### 11. Gateway outages cost more than they should, and the launch-time repair aborts on them
Severity: wastes-time.
Where: cloud_sync.rs:561-575 (retries only 502/503/504, 2 s + 4 s), orchestrator.rs:69 (supervisor retries 5xx/407/429 and transport, six tries), lost.rs:421-443 (`spawn_check`) and `check` (lost.rs ~163: `sync(...)?` first).
Scenario: Blaxel standby resume can exceed 6 s; transport errors are not retried at all in the app. `lost::check(Full)` runs once per launch (`sync_on_start`); if its first `sync` fails (502, DNS), the whole check returns `Err`, is logged as WARN, and is not retried until the next launch: lost sandboxes are not replaced and stale node sandboxes are not reinstalled for the whole session (a later `Check::Marked` only runs after a successful sync that brings a lost mark).

Test: yes: `cloud_sync/tests.rs` with a stub server that returns 502 twice then 200; and a `check` that fails then succeeds.

### 12. A 5xx is reported as a problem and announced, which can feed itself; malformed `/changes` is a 500
Severity: wastes-time.

### 13. Problems channel loses lines at rotation and duplicates on partial pushes
Severity: wastes-time.
Where: tod-problems/src/lib.rs:162-177 (`files` lists only `*.jsonl`, so the rotated `*.jsonl.1` is ignored), :90-99 (`write_json` renames over an existing `.1`), :183-205 (`read_since` treats `len < offset` as rotation and rereads from 0), orchestrator problems.rs:33-60 (`push` stores one by one and returns 500 or 400 after earlier items were stored).
Scenarios: lines between a reader's cursor and the rotation go into `.1` and are never read (up to 13 KB right now for the app's `tod-orchestrator.jsonl` cursor). ## Part C. Design changes that remove whole classes of failure

1. **A compatibility contract instead of source hashes** (A3, findings 1, 3, 19): `/health` and every request carry `{wire, schema, build}`; the orchestrator, app, daemon and supervisor refuse (426 with the fix) rather than half-apply; migrations stay additive within a `wire`. One mismatch can then never wedge sync or destroy the database.
2. **Apply row by row with a quarantine** (finding 1): a rejected row never blocks the rest; both directions; always visible as an ERROR with table/key/reason.
3. **Ownership recorded, never inferred** (findings 2, 7, 14): the orchestrator database knows which data root seeded it and which data root owns each node (`workspace_id`, `owner_client`, repo). Seeds from another root are refused; broker requests go only to the owner; webhooks route by (user, repo, branch), not by branch name alone.
4. **The orchestrator never does slow work inside a request** (findings 4, 10, 15): pokes, GitHub looks and retries go to worker pools with their own timeouts, deadlines and panic restarts; handlers return after commit.
5. **A bounded log** (finding 6): prune `sync_changes` by acknowledged cursors, never log big unchanged columns, send `conversation_live` out of band, strip the log from snapshots, page the feed.
6. **A pull path that does not depend on a third party** (finding 8): app/daemon hold `GET /changes?wait=25` against the orchestrator (the daemon already holds the broker's long poll, so the "must not be held open" premise is already gone while a database is declared); ntfy only for phone alerts; mark a notice announced only after a successful publish.
7. **One retry/deadline policy** (findings 5, 11) shared by app, daemon, supervisor, scheduler: transient errors including transport ones retried to ~60 s; no mutex held across the network; heartbeats independent of pushes.
8. **Daemons with a lifetime** (finding 18): exit when the data root is gone or idle; prune build copies; do not sync or answer for a different build.
9. **One problem channel with de-duplication and escalation** (findings 12, 13, 17): the orchestrator and the wake timer report through it; repeats collapse but a streak of N escalates to a toast; rotation never drops lines.
10. **Durable orchestrator state by default** (findings 3, 8, 10): a volume for /data, atomic seed state, and an app-side reconcile after any NOT_SEEDED/new process id (re-register wakes, refetch the notify topic, reseed only with confirmation).
