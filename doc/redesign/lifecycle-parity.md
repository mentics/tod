# Default lifecycle parity verification

Default can move from the legacy lifecycle to the workflow engine once both paths produce equivalent user-visible outcomes for the same task, configuration, and observations. This includes states, waits, evidence, side effects, and resumption after interruption. A route in the graph establishes its destination. Its action, inputs, and gate still need to establish why that route is taken.

The audit below compares legacy execution with the operator-driven `default_template()` and the automated candidate `automated_default()` as of November 24, 2026. It records implementation evidence, observed comparisons, and acceptance cases. Full phase parity remains open. Until then, the legacy lifecycle remains the Default execution path.

The rollout targets local devcontainer tasks. A task whose effective Files location is a cloud sandbox continues with legacy automation. The workflow panel retains saved history and supports detachment for those tasks.

## Phase verification matrix

| Phase | Legacy contract | Operator template coverage and open gap | Acceptance cases |
|---|---|---|---|
| Proposed | Require at least one own requirement and a current assessment of the task's obligations. Request missing intent from the user. Evaluate the work independently when configured. | The shared requirement check holds the route until there is at least one own requirement. The action is manual. Needs the intent request and a certificate tied to the current obligation inputs. | Test a task with inherited requirements only, an empty task, duplicate or conflicting requirements, and an edit after certification. Valid requirements advance once. |
| Design | Certify the current design from task obligations, design content, and mockup input. An unchanged input can restore a suspended certificate when the task returns. | Manual action and forward route. Needs a design action, independent evaluation policy, and matching certificate evidence. | Change obligations, content, and mockup independently. Re-enter after a redesign request with unchanged input and then with a changed design. Compare the certificate and outcome. |
| Planning | Certify the plan and require plan coverage for obligations implemented through plan steps. Record a baseline as the task enters Ready. Changes to obligations and plan steps can reopen planning. | The shared coverage check reads the current plan links and holds on uncovered requirements. The action is manual. Needs plan certification, baseline capture, and invalidation. | Cover an Active requirement with a linked step, then remove the link or edit the step. Include a requirement that only acts in Design or Verifying. Add a requirement after Ready. |
| Ready | Use the effective Agent and Files settings, provision the configured workspace when needed, and resolve generated branch names. Missing configuration or a busy workspace can prevent execution. | A reusable workspace action generates the branch and checks effective Agent and Files settings using the legacy rules. Workspace creation remains deferred until first use. Needs comparative inherited, deferred, missing, and busy workspace cases. | Compare directly configured and inherited settings, generated branches, a deferred worktree, a missing directory, and a busy workspace. |
| Active | Run implementation for due plan steps and require at least one due step and completion of all due steps. Run prerequisite checks and repair when configured. Pause when blocked or when work cannot make progress. | The shared plan check requires the due steps to be implemented. The action is manual. Needs plan-aware implementation dispatch, check setup and results, and protection against lost work. | Compare due and later-phase steps, missing plan work, a failed setup check, a worktree lock, and commits removed from the work branch. |
| Verifying | Verify due steps and obligations and audit verification evidence when configured. A failed step returns to Active. A failed obligation without a failed step keeps the task in Verifying. Stale evidence and repeated failures need explicit handling. | Manual Boolean output routes a failure to Active. Needs separate step and obligation outcomes, validity and audit, retry and no-progress outcomes. | Test a failed step followed by repair, an obligation-only failure, a rejected evidence audit, revised code that invalidates evidence, and repeated failure across a restart. |
| Review | Run main and risk reviews over the same work and opening context. Fix findings, verify fixes, and review the new revision. Pass on a current clean review with no remaining findings. Escalate repeated root causes or growing findings to Design. | Separate Review, Fix, and decision nodes. The graph compares reviewed revision with the current clean checkout, branches on open findings, and can return to Design. Review outcomes and escalation are entered manually. Needs both reviewers, finding acknowledgement, quick-fix and escalation policies, and persisted convergence evidence. | Compare clean pass, finding then fix then clean pass, clean result for an old head, dirty checkout, mechanical quick fix, duplicate or reappearing findings, and three rounds with a recurring root cause. Record both reviewers' opening inputs. |
| PR | Ensure the branch is pushed, open or discover a draft PR, and certify the current stay even when a PR already exists. | Manual action and forward route. Needs draft creation and recovery, per-branch PR linking, and stay certification. | Paired fixtures cover recovery of an existing branch draft whose link was lost and fresh certification on re-entry without reopening the PR. Still compare mixed repositories and a link belonging to a different branch. |
| PR Draft | Babysit drafts through configured checks, bots, optional TOD review, and human readiness or reviewer assignment. Track PR heads and avoid duplicate work when waiting. | Manual action and forward route. Needs babysitting, head-aware check and review evidence, skill dispatch, and external wake conditions. | Paired fixtures cover ready-for-review, a human reviewer request, and optional TOD review of a feedback repair before pushing. Bot and TOD-account assignments do not satisfy the human gate. Still compare live GitHub writes and a head change during a draft wait. |
| PR Review | Evaluate mergeability, up-to-date status, required checks, review threads, current review results, and repository thresholds. Respect qualified waivers and run configured phase groups before waiting for people. | Manual action and forward route. Needs GitHub readiness facts, policy and waiver evaluation, feedback handling, and human waits. | Paired fixtures cover two PRs in different wait states, feedback repair before pushing, and a base-proven failing check waived for one head only. Still compare behind heads, required bots that skip drafts, and live GitHub failures. |
| Approved | Wait for every linked PR to merge and resume when GitHub changes. Missing PR links and unreadable snapshots must not falsely certify the merge. | A GitHub provider gates departure on all linked PRs reporting merged and exposes a scheduled wait through Autopilot. Needs comparative testing of event-driven wake, missing links, recovery after a transient failure, other failure categories, refresh, and multiple PRs. | Hold with one of two PRs unmerged. Merge it, deliver a wake, then repeat after a restart and with a transient read failure. Paired fixtures verify that malformed links produce the same human-facing gate failure and cannot certify a merge. Test a task with no linked PRs. |
| Merged | Observe published releases for repositories that release. Match release notes to the task's merged PRs and respect repository release policy. Require current certificate, verified due steps, and verified due obligations. | Manual completion can leave once the GitHub provider observes published releases for linked PRs under the legacy repository policy. Autopilot exposes a scheduled wait while release evidence is pending. Needs comparative event wakes and scoped verification. | Paired adoption fixtures cover no-PR release work, unrelated release notes, and mixed merge-only and releasing repositories. Malformed links remain visible in the trace. Both engines run ordinary Merged certification when links cannot support GitHub release tracking. Still compare draft and prerelease filtering and outstanding Merged verification. |
| Released | Record smoke and verification evidence for the released work. Require a certificate for the current stay and verified due steps and obligations. | Manual action and forward route. Needs post-release smoke checks, certificates, and scoped verification. | Cover missing smoke results, a prior stay's certificate, independent evaluation, and a newly introduced Released obligation without a passing verdict. |
| Learn | Capture retrospective learning or an explicit none outcome for the current stay before completing. | Manual action and forward route. Needs equivalent retrospective recording and linkage to improvement artifacts. | Compare meaningful learnings, explicit none, and retrospective evidence from an earlier stay. Confirm that an improvement proposal retains links to the producing run and inputs. |
| Done | End lifecycle dispatch and retain the completed task and evidence. | The automated candidate projects Done and closes the workflow with the terminal result. | Compare task state, run result, completed conversation cleanup, and reopening. |

## Side-by-side execution

Run `cargo test -p tod-core autopilot::tests::default_parity` to compare two independent task stores using the same fake agent and, where applicable, the same GitHub observations. Both use the normal Autopilot entry point. The tests seed the same starting phase. A graph starting after Proposed retains reachable nodes, actions, routes, and provider bindings from Default and publishes that graph with the tested phase as its entry. The fixture retires criteria that require external agent configuration or separate PR-opening and review setup. These checks cover only the listed boundaries.

| Scenario | Legacy result | Operator-driven Default result |
|---|---|---|
| Empty Proposed task | Starts its proposal agent, stays in Proposed, and writes one free-text intent request. | Stays in Proposed with a manual action pending. No agent turn or intent request. |
| Approved, linked PR remains unmerged | Stays in Approved and schedules a merge wait without starting an agent. | Stays at the Approved workflow node and schedules a merge wait without starting an agent. |
| GitHub repeatedly returns HTTP 503 before merge | Stays in Approved, persists each retry, and exhausts the retry budget before reporting the failure. | Stays in Approved, persists the same attempt numbers and scheduled reads, and reaches Error at the same limit. The final Autopilot outcome matches legacy, the trace retains the provider error, and the graph clears its scheduled wait. |
| Merge confirmed | Continues into Merged and schedules a release wait without starting an agent. | Enters Merged and requests manual completion before evaluating release evidence. |
| Release notes omit the linked PR | Stays in Merged and waits for a matching release. | Stays at Merged and schedules the same kind of wait once the test explicitly supplies the required manual acknowledgement. |
| Release notes identify the linked PR | Finishes release and retrospective automation, reaches Done, and clears the pending wait. | Records the matching release URL and reaches the manual Released action. The fixture supplies no further manual results. |
| Existing review work | Starts Main and Risk review conversations, records findings, and starts Fix. | Stops at a manual Review action without a review turn or persisted finding. |

### Automated candidate observations

- Both engines issue the same free-text intent request on an empty Proposed task and use the same number of fake-provider turns.
- In a disposable Docker devcontainer, both engines advanced from Proposed to Design after a deterministic ACP adapter called the production `tod-cli` shim. The host daemon saved exactly one certificate with ACP conversation provenance for each run. Concurrent shim installers now use separate temporary files. A Docker regression test verifies that every install succeeds and the final file is complete and executable.
- The configured Codex adapter also advanced both engines from Proposed to Design in Docker and saved one certificate with conversation provenance per run. The disposable fixture needed working Linux user namespaces, a resolvable host relay, and approval for the certification command’s relay retry. An earlier probe without the identical retry instruction produced different agent responses to the same sandbox restriction.
- A request opened by the legacy Proposed agent can be answered after adoption. Both engines record the answer as a requirement, reach Design, and continue to Planning after the adopted task is returned to legacy.
- Both engines start from Approved, wait for an unmerged PR, wait for release notes that mention it, and reach Done when the matching notes arrive. The automated graph projects Merged and uses no manual completion in this scenario. Its merge and release waits persist with separate visit identities and are cleared by completion.
- Both engines take the configured mock task from Proposed to Done with the same conversation counts for implementation, verification, review, fix, and PR. Both link the same single fixture PR and record the same PR certificate event kinds and certifiers. The graph captures both reviewers’ matching shared opening under the Review visit and uses no manual completion.
- Repeatedly failing the same obligation keeps both tasks in Verifying. Both stop at the same verification round with the same loop reason and the same persisted fix count.
- A recurring review root cause sends both tasks from Review to Design after three review rounds. Each transition cites three recorded findings. The reason text agrees after normalizing the finding IDs from the independent test stores.
- Both engines can repair draft and review feedback locally, review the change, fix findings, review it again, then push the reviewed head and resolve the thread. While one PR waits for a reviewer, both engines keep polling a second PR’s checks until they finish. A requested human reviewer clears the draft gate and starts PR Review. A check failure also present on the base is waived once by TOD, advances to Approved, and remains scoped to the observed head.
- Approved with no PR link produces the same actionable gate failure in both engines, with no agent dispatch or timed poll.
- Both engines invalidate the Design certificate independently on an obligation, mockup, or design edit. Both restore the unchanged certificate after an operator moves the task back to Design and recertify a plan whose obligation coverage changed before recording its Ready baseline.
- Both engines schedule the same retry on a worktree lock and repair a failing configured implementation check before entering Verifying. Both can quick-fix a failing Review check before the reviewers open. The workflow records the repaired revision as the review input. A confirmed phase move changes the task and graph cursor in one transaction. Reopening a completed task starts a fresh run on the pinned revision and leaves the completed run and its evidence available in history.
- When Files resolve to a cloud sandbox, a saved workflow cannot dispatch and the legacy runner continues. The local exclusion fixture verifies that workflow assignment and adoption are refused and that a previously attached run can still be detached.
- The local daemon picks up new workflow waits from the UI or CLI and restores the current visit’s durable wait after a restart, even when the Autopilot checkpoint was never written. Explicit pauses survive. Operator moves invalidate the old wait and update the dashboard. Detaching transfers the matching deadline to the legacy runner.

These comparisons use fixture PR responses and a fake agent. Before cutover, compare the remaining release, review, and runner cases against the automated candidate.

- An existing Merged stay starts at the release evidence gate. The handoff fixture verifies that rollback restores the pending release deadline to that same stay. The paired fixtures verify no-PR release work and mixed repository release policies, including the same status for each PR in the wait. A valid PR with no matching release waits. When links include malformed data, both engines continue through ordinary Merged certification and the workflow trace retains the invalid-link diagnostic. The same malformed input in Approved yields the legacy gate failure and cannot certify the merge. Verify these paths with the real provider before cutover.
- Both engines consumed the same real GitHub merge observation from an existing PR in the disposable test repository and advanced to Merged without an agent turn. The automated PR fixtures use simulated GitHub for writes and changing state. Live PR writes, repository-specific bot thresholds, and head changes during an external wait remain open for the devcontainer path.

### Resumed devcontainer comparison against main at `6d0a1d79`

The integrated candidate passed the 27 deterministic parity and scope cases again. The CLI adoption and rollback smoke test, durable daemon wait recovery, ZGX live build, and the three new conversation answer regressions also passed.

After Codex sign-in was restored, the saved tasks continued in separate checkouts inside the signed-in devcontainer. Each completed Planning, implementation, verification, and clean Main and Risk reviews on its own revision. These cases used simulated GitHub observations, as accepted for this integration.

## Verification across phases

| Concern | Evidence to compare |
|---|---|
| Task state, history, and cutover | Explicit adoption uses a published start node for the task's current stay. An existing Review stay starts by capturing the current review input. The stay, open human decision, and evidence survive adoption, revision change, and detachment. A paired local run continued from the human answer and rolled back at Design. A stale preview is refused after the task leaves and re-enters the same phase, even with equal timestamps. An existing Merged stay starts at the release evidence gate and rollback restores its legacy deadline. Detachment preserves a completed task's Done stay and run result. |
| Instructions and learning | Record the exact prompt, selected skill revision, configured skill groups and their order, inherited context, and dynamic source contents used by each action. Compare legacy prompt inputs against the workflow transcript. After publishing an improvement, reproduce the original input and result from history and show that new work adopts the explicitly selected revision. |
| Invalidation and provenance | Change obligations, plan steps, checkout state, and GitHub head independently. Compare what stays valid, what is withdrawn, and where the task resumes. Check certificates against the same task stay and relevant inputs. Tests should retain exact IDs, revisions, observations, and verdicts. |
| Execution, waits, and controls | Exercise interactive ZGX, CLI, and daemon entry points using configured devcontainer execution. Compare permission and question requests, cooldowns, pause/resume, waiter ownership, wake on new evidence, stale results, and retry limits. Check that repeated sessions consume the persisted Autopilot budget and that a resume with a renewed budget keeps prior evidence. Resume across a daemon restart and confirm one effect for each PR mutation and command execution. |
| Compatibility with main | The candidate combined with `main` at `6d0a1d79` passed the parity and scope suite and the CLI cutover smoke test. Both Default runtimes reached Done in the configured-provider devcontainer smoke test. |
